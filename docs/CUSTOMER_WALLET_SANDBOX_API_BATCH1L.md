# Batch 1L — durable test-only customer wallet checkout API

This batch adds a separate sandbox checkout API. It is NOT live collection, a deposit into a spendable wallet, or ledger settlement. Sandbox attempts are deliberately separate from wallet_topup_attempts, wallet_business_events, wallet_movements and legacy wallet_transactions. No successful sandbox payment can be counted by cash-credit qualification or financial reconciliation. Verified state is verified_test_only, and every customer response says testOnly=true/spendableCredit=false. No balance or earnings is credited.

Existing startup KORA_SECRET_KEY configuration remains. The service requires its mode to be test before preparing a request; a live key is refused before DB/provider contact. No credential, mode, provider, merchant, country, currency or email override is accepted from clients. POST /api/wallet/sandbox-topups accepts exactly idempotencyKey UUID and amountMinor positive bigint-range string. Bearer identity and email confirmation come from Supabase. The server-only SQL wrapper locks the activated customer profile, approved test cohort and registered market; it requires an existing matching wallet, canonical currency exponent, live customer capability, a bounded test amount, and unambiguous city/country selection. A paused city cannot fall back. Actual Kora currency/product support still requires explicit test-cohort approval; arithmetic support does not establish provider approval.

New protected tables: customer_wallet_sandbox_cohort_v1l (per-owner tenant/country/currency/exponent/max limit, default disabled), customer_wallet_sandbox_attempts_v1l (frozen mode=test, reference, merchant, fingerprint, exact money, lifecycle). RLS enabled with no client policies; raw service table writes are revoked. Controlled RPCs are service-only. Metadata-free clients cannot invoke them. Schema migration creates no gate row/cohort, enables no route, replaces no existing RPC and refuses a second application/conflicting tables transactionally rather than silently replacing them.

A unique (owner,idempotencyKey) record is committed before the separate atomic submission claim. The claim rechecks sandbox gate/cohort; only its winner can POST. Terms freeze includes test mode and startup credential fingerprint; a changed key/account cannot retarget an existing attempt. Timeout or reference-record failure leaves submitting/uncertain and never blindly repeats creation. Poll GET /api/wallet/sandbox-topups/:id returns own safe state. POST /api/wallet/sandbox-topups/:id/reconcile takes no evidence fields; it queries Kora by the persisted reference and verifies exact amounts/currency/reference. Reconciliation remains possible after the sandbox admission gate/cohort is disabled. Pending/unknown remain recoverable; verified/failed cannot be downgraded by late notification. No sandbox refund or live payment capability is installed.

POST /api/wallet/sandbox-topups/kora/webhook checks x-korapay-signature against data with startup test key, resolves the persisted reference and STILL performs a provider GET. Notification amount/status are not evidence. Unknown signed references receive a generic acknowledgement. Unsigned fields never select an operation. No raw provider response, secret, credential fingerprint or merchant reference is exposed. Existing API handlers are byte-preserved. Rate limit 20/minute; private/no-store and Vary Authorization headers; generic storage errors.

Admission key is wallet_collection_config.customer_wallet_sandbox_enabled, absent/false by default. Cohorts also start empty/disabled. This gate is separate from and does not modify customer wallet setup, wallet collection, cash pilot, merchant live approvals or production routes. No flag/cohort is enabled by this package. A future reviewed sandbox run needs a test-only cohort and server callback URLs. Callback slots remain KORA_COLLECTION_RETURN_URL and KORA_COLLECTION_NOTIFICATION_URL; no environment value is changed by this package. Merchant approval booleans passed to the transport represent sandbox cohort admission only, never live payment approval.

Locally executed: 24 new service/actual-route mocked cases, existing 30 startup transport + 33 readiness + 20 wallet setup cases (107 total); exact writer/Stripe/startup preservation; installer install/reinstall/rollback; shell syntax; extracted checksums. External HTTP/auth/DB boundaries mocked. Real PostgreSQL test, independent-session barrier concurrency, project Vitest/full TypeScript and Docker compilation are NOT RUN here. Owner isolated runner executes on fresh PostgreSQL 15 with network none/no application volumes, plus mocked tests in current API image via stdin extraction. The fixture reproduces relevant columns/roles, not full Supabase auth bootstrap. SQL verifies real service/client privileges, idempotency/conflicts, claim exclusivity, bounds, market/role/currency/activation, frozen history and unchanged legacy wallet rows. No application DB or provider connected by the runner.
