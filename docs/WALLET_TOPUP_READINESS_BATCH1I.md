# Batch 1I — read-only customer top-up readiness

This is the readiness phase of collection integration, not a working payment checkout. Owner preflight: customer setup enabled; collection/cash pilot disabled; GB/GBP and NG/NGN live; 19 collection routes all disabled/unapproved/not ready with no collect capabilities; Kora merchant references absent; no per-currency limits; no attempts. No provider eligibility is invented.

Adds GET /api/wallet/topup-readiness to the existing wallet router. Bearer identity is verified with Supabase; owner/country/currency input is rejected. Reads only: profile, registered market, existing wallet, two allowlisted configuration keys and card collection routes. No SQL migration, RPC writer, provider contact, credential read, gate/approval change, wallet creation, money movement or UI/layout change. Existing wallet setup and all financial route bodies are preserved. Private merchant references are tested locally for presence and never returned. Auth/rate-limit/no-store headers apply; SQL details never returned.

Currencies come from the active registered country/city market, with expiry, live customer capability, duplicate rejection and paused-city blocking. Address country is not authority. Any configured three-letter currency is supported, not a GBP/NGN list. An existing wallet with a different recorded currency blocks readiness, without conversion. Kora, Stripe and Fincra share readiness rules; this does not imply these providers support every currency. A deployment must still verify each provider/account/currency/product with provider evidence.

All results have canSubmit=false and collectionAvailable=false because this batch does not install the collection transport/writer. Even fully configured routes return collection_integration_pending. The maxAmountMinor limit is an exact positive bigint-range string, not a JS number or a minimum amount. No balances, merchant IDs, keys or provider evidence returned. Route selection matches current Batch 1C card/preferred/enabled/approved/adapter-ready/collect requirements; readiness is informational and cannot authorize collection. Separate reads are not a transaction snapshot; future submission must revalidate atomically through Batch 1C.

Executed locally: 33 production-service/actual-route behavioral cases using mocked auth and database; nine configured currencies; route capability, exact limits, market hierarchy, owner isolation, mismatch, fail-closed and secret suppression. Installed/reinstalled/rolled back in a scratch fixture; exact pre-existing route preserved; shell syntax and archive checksums verified. Not run here: project Vitest/TypeScript or Docker image build. The owner runs full server startup compile and the image build; isolated runner runs the same mocked behavioral suite in an existing API image with no network or application volumes.

Image builder requires the deployed Batch 1H image b9ec6e123ae2878ba1a88f9cb4e2a480b6753b120d227a7a6d8e760fe05a76dc and verifies the exact original wallet router before overlaying only the new service/router. Candidate only: movabi-api:wallet-topup-readiness-v1i. No restart/deploy.

Next collection phase still needs merchant-approved account/provider capabilities, limits and real verified transport/repository wiring, plus settlement destination reconciliation. Do not accept real deposits into the diagnostic-only ledger. No approval, live route or spendability is enabled by this package.
