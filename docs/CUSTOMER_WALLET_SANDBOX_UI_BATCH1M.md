# Batch 1M — approved-customer wallet sandbox control and return handling

Adds one compact test-only component inside the existing customer Wallet page. Balance, real payment writers, transaction list, old Stripe controls and driver/dashboard layout are preserved. No amount is posted to a spendable wallet. The existing real-top-up retirement notice remains because the new control is explicitly a sandbox exercise, not live funding.

The control is hidden unless verified API eligibility approves the signed-in customer, test startup key, merchant config, confirmed email, active cohort, registered market, existing matching currency wallet and limits. The new read-only service-only customer_wallet_sandbox_eligibility_v1m RPC validates scope and market hierarchy; live/ambiguous/paused-city/mismatched/pending cases fail closed. GET /api/wallet/sandbox-topups/eligibility is registered BEFORE /:id. No client table grants or direct client RPC execution. No new approval/cohort, gate update, provider request or money movement occurs from eligibility reads.

Sandbox amount comes from that customer's configured test cap and currency/exponent. No GBP/NGN-only UI mapping, floating-point conversion or global display-currency preference. The fixed test button labels its exact configured amount; it is not an unrestricted real-deposit form. Actual Kora product/currency approval remains a separate sandbox-cohort decision. Return origin must match the current app origin; a native or other-origin environment is not silently redirected into the web app. Existing Stripe booking/payout behavior stays unchanged.

The client keeps owner-scoped idempotency/attempt IDs in sessionStorage, never tokens. It verifies the current SDK session owner before request, then checks owner generation after every await. Double clicks, stale responses, account switches, unmounted components, mismatched terms, unsafe URLs and claims of spendable sandbox money fail closed. Hosted checkout navigates in the same tab. The configured return is /customer/wallet; a strict vaydu_test_<32hex> reference can locate its attempt but NEVER establish success. The server first verifies ownership, then reconciles through persisted terms. Successful status says Sandbox payment verified. No money was added to your wallet. Query reference is removed only after ownership is verified and recovery context saved. Pending results have an explicit Check test status button; there is no unbounded polling. Existing saved attempts are reconciled rather than blindly re-created, including unknown POST outcomes.

Automatic eligibility load is read-only. Opening a returned attempt may trigger the existing server-side provider GET reconciliation; never a new checkout POST. A test is started only by the customer's button click. The migration/application/deployment scripts do not change gates, existing cohorts, merchant approvals, callback URLs, keys, Stripe or cash pilot. The already-approved single test cohort stays subject to the existing server admission gate; this package does not broaden it.

Executed locally: 24 pure production-client lifecycle cases, 11 production service/actual-route eligibility cases, existing 107 mocked regressions (142 total); exact existing source preservation, installer install/reinstall/rollback, shell syntax, archive checksums. External HTTP/auth/database dependencies mocked. Angular component itself requires owner's full mobile/admin builds. PostgreSQL isolated eligibility tests, full project Vitest/TypeScript and candidate Docker build NOT RUN here. Isolated runner uses fresh PostgreSQL 15, network none, no application volume, representative Batch 1L fixture + original 1L migration + read-only 1M function. It checks real function permissions, scope, canonical exponents, duplicate market/paused city and no new attempt/balance changes; it does not recreate all Supabase auth bootstrap behavior.

Build base is the deployed Batch 1L image 5184d0ce42a7933ef72d0368ef62ddee601f0cd13ce0c6ec6942786a9a339a0e. Separate local-source and deployed-image baselines avoid copying local startup/sandbox/Stripe differences into the image. Payload changes only wallet router and sandbox service. Existing deployed index, Stripe service and startup credential transport are exact-hash guards, not replacements. Web release is built from the local project by the owner; no driver UI file is in the installer. Candidate only; no automatic database migration, deploy, activation, provider call, key change, staging or commit.
